# 0002. The container owns network sensors and the agent owns COM ports

The service runs in a Linux container on the Windows trailer computer, and a Linux container cannot open Windows COM ports. We therefore split acquisition by transport: the container reads sensors it can reach over the network or a file, namely the EKO C-BOX over Modbus TCP and the JETI LiVal capture file bind-mounted read-only, while any device that needs a COM port (the T-10A, and JETI with `transport: "serial_scpi"`) is marked `"acquisition": "external"` in `sensors_config.json` and read by the native Windows Sensor Agent (`svc/scripts/sensor_agent.py`, started by `scripts/sensors/Start-SensorAgent.ps1`). The agent reads the same configuration, polls only the external devices, and forwards authenticated, idempotent batches to `POST /sensors/ingest` through a durable outbox; `SVC_SENSOR_INGEST_TOKEN` must match on both sides. The container registers external devices but never opens them, remains the only process that writes the production `audit.db`, and reports an external sensor as degraded in `/health` when the agent's data is missing or stale. This keeps one database writer and one configuration file at the cost of a second process to install and monitor on the Windows host; if no device is marked external, the agent is not needed. See `docs/production_sensor_setup.md`.
